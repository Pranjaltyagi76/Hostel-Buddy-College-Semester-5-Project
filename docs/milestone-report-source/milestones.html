2. Purpose of This Report

This report records how Hostel Buddy was built, milestone by milestone. For each of the four checkpoints — 30%, 60%, 80% and 100% — it states which development phases were completed, how the architecture grew, which bugs were found and fixed, and how the work was verified. Every claim is traceable to a commit in the project's Git repository.

Development model used

The project followed the Incremental Model. Requirements were fixed first in an approved SRS, the architecture was designed before coding, and construction then proceeded in seven increments (Phase 0 – Phase 6). Each increment produced working, tested software rather than a half-finished layer, so the system was demonstrable at every checkpoint.

Why incremental and not Waterfall? Because defects were caught during construction and fixed before the next phase began — not discovered at the end. The repository shows this directly: a dedicated Review fixes commit sits between Phase 2 and Phase 3.

4.3 How the architecture was set up here

The layered architecture was established at this milestone and never changed afterwards — later phases only added modules that follow the same shape:

Database: two tables were created — users (in active use) and complaints (created and waiting for Phase 2). Constraints were placed in the schema itself: unique email, a foreign key from complaint to user, and CHECK rules limiting role, category and status to valid values.

4.4 Bugs and problems at this stage

B2 — Login revealed which emails were registered. Different messages for "no such user" and "wrong password" let an attacker discover valid accounts. Fix: one generic 401 Invalid email or password for both.
Lesson: security errors should be deliberately vague; usability errors specific.
Environment problem — the database driver would not install. The design named better-sqlite3, which compiles C++ and failed without Visual Studio build tools. Fix: switched to Node's built-in node:sqlite. Benefit: any team member can clone and run the project with no compiler. Recorded as decision D5.

4.5 Verification

The login module was covered by tests/auth.test.js — 24 automated checks, all passing, including that the password hash never appears in a response, that a wrong password gives a generic error, and that a student cannot reach admin-only endpoints.

Viva point. "We built authentication before any feature, because authorisation is not something you can add afterwards — every later endpoint needed a trustworthy answer to who is calling."

5.3 How the architecture developed

The structure did not change — it replicated. Each new module repeated the same four-file pattern, which is exactly the benefit the layered design was chosen for.

Module addedDesign decision worth explaining
Complaint ManagementThe rule "edit only while Pending" was placed in the Service, not the route. A route-level check protects one route; a service invariant holds for every caller, present or future.
DashboardGiven no repository of its own. It reads counts published by the Complaint and User modules, so reporting cannot break when a table changes. Counting is done in SQL (GROUP BY), not in JavaScript.

Source files grew from 20 to 29 across these phases, while the number of architectural layers stayed at five — growth was horizontal (more modules), not vertical (more complexity).

5.4 Bugs found and fixed at this stage

A deliberate review was carried out after Phase 2, before continuing. This is the clearest evidence of incremental development in the repository — the fixes have their own commit, 7668bc8.

Problem foundWhy it happenedFix
Seed script was brokennpm run seed pointed at a file that did not exist — an advertised command that crashedWrote the seed script; it now loads an admin, 5 students and 13 complaints, and is safe to re-run
Insecure defaults could reach productionA missing JWT secret or default admin password only produced a warningThe server now refuses to start in production with insecure settings
Duplicate-email raceTwo simultaneous registrations could slip past the check and hit the database constraint, returning a 500The constraint violation is caught and returned as a clean 409
B3 — resolved_at was overwritten on every later update. Re-saving a Resolved complaint kept moving its resolution time, and closing it reset the date. Root cause: the field was assigned unconditionally instead of "set once".
Fix: it is written only the first time a complaint reaches Resolved. Lesson: "the first time X happens" is a different rule from "whenever X is true".
B4 — The client was trusted with its own status. A crafted request could create a complaint already marked Resolved, skipping the workflow. Fix: the service ignores any status sent by the client and forces Pending. Lesson: never let the client set a field the workflow owns.
B6 — Tests silently depended on leftover data. Suites passed alone but failed when run after one another, because they assumed a pristine database. Fix: every suite now creates its own students and complaints and asserts changes rather than absolute totals. Lesson: a test that only passes first is not really passing.

6.3 The audit — how we tested

The running application was attacked deliberately: 237 probe requests with malformed and hostile input, followed by a browser walkthrough of every page at desktop and mobile widths.

What held: SQL injection, cross-site scripting, JWT forgery, mass assignment, ownership isolation and path traversal — all resisted. Zero 5xx responses were produced.
What broke: the ten defects below. Each one is now pinned by a permanent check in tests/regression.test.js so it cannot return.

8. How the Architecture Developed

The single most important architectural fact is that the layered structure was decided once, at 30%, and never had to be changed. Later milestones added modules into that structure rather than reshaping it.

9. All Defects at a Glance

Seventeen defects were found, fixed and documented across the project. Grouping them shows when each kind of problem surfaces.

MilestoneDefectsCharacter of the problems found
30%B2 + environmentSecurity disclosure and tooling. Login revealed valid emails; the database driver would not install without a compiler
60%B1, B3, B4, B5, B6 + 3 review fixesBusiness-rule correctness. Timestamps overwritten, client-supplied status trusted, broken seed script, insecure production defaults, order-dependent tests
80%B7, B8 – B17Everything the happy path never touches. Type confusion, unenforced state ordering, spoofed uploads, leaked framework errors, search wildcards, truncated passwords, disabled rate limiting, an unreachable requirement
100%Dependency advisorySupply chain. A third-party package with a known high-severity vulnerability
The pattern worth explaining in the viva. Early milestones produced logic bugs, which our own tests caught. The 80% audit produced assumption bugs — places where we had trusted the client, trusted a type, or trusted that a documented rule was an enforced rule. Tests written from a design cannot find those, because they share the design's assumptions. Only adversarial testing does.

11. Conclusion

Hostel Buddy was completed through four verified milestones over roughly six weeks. The foundation and authentication were established first (30%), the complete business logic was proven through the API next (60%), the interface was integrated and the system was then audited against hostile input (80%), and finally everything was joined, automated and documented (100%).

The project's strongest evidence is not that it works, but that we know why it works: seventeen defects are recorded with root cause and fix, one hundred and forty-five automated checks pin the behaviour, and every one of the audit findings has a permanent regression test standing guard over it.

Closing statement for the viva. "We treated finding bugs in our own work as a deliverable, not an embarrassment. The audit at 80% found ten defects that our green test suite had missed — and documenting each one with its root cause is what turned this from a project that runs into a project we understand."
